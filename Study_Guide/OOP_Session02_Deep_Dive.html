شرايح 3 – 10

1) Class كـ Reference Type

تشبيهالـ reference زي عنوان شقة على ورقة. الورقة (المتغير) بتتخزن في جيبك (الـ stack)، لكن الشقة نفسها (الـ object) في مبنى بعيد (الـ heap). لو صورت الورقة ووزعتها على صحابك، كل واحد فيهم عنده عنوان الشقة نفسها: أي حد يدخلها ويغيّر فيها، الكل هيشوف التغيير لأن الشقة واحدة.

1.1) الأربع خطوات (الشريحة 6): دقيقة، لكن فيها تفصيلة تستاهل توضيح

الشريحة رتّبت الخطوات صح:

  1. حجز البايتات المطلوبة على الـ Heap.
  2. تصفيرها لقيم الـ default بتاعة النوع.
  3. نداء الـ constructor (المعرّف من المستخدم، أو الـ default لو ما فيش).
  4. تعيين عنوان الـ object للـ reference.
الميكانيزم الدقيق للخطوة 1: مش زي malloc

الـ heap بتاع .NET (Gen0 تحديدًا) بيشتغل بـ bump allocator: مؤشر واحد بيأشر على أول بايت فاضي، والحجز هو مجرد pointer += size. عشان كده حجز object جديد في .NET من أسرع العمليات (أسرع من C++ new بكتير غالبًا)، لأنه مش بيدوّر على "فراغ مناسب" زي الـ heap التقليدي. الجزء المكلف هو الـ Garbage Collection اللي بييجي بعدين، مش الحجز نفسه.

1.2) تصحيح تفصيلة: "4 | 8 bytes ... Depend on OS"

تصحيح دقيق

مش الـ OS هو اللي بيحدد حجم الـ reference، لكن معمارية الـ process (x86 مقابل x64/ARM64) اللي التطبيق شغّال عليها. تقدر تشغّل تطبيق x86 (32-bit) على ويندوز 64-bit، وهيفضل الـ reference حجمه 4 bytes. الحجم الفعلي هو IntPtr.Size: 4 على x86، 8 على x64 وARM64. الشريحة قصدها صح، بس المصطلح الدقيق "target platform / process bitness" مش "OS".

1.3) العناوين في الشريحة (0x001) تبسيط تعليمي، وفيه فخ حقيقي وراه

مفهوم غلط خطير: "العنوان ثابت"

الشرايح 6-8 بترسم العنوان (0x001, 0x002) وكأنه ثابت طول عمر الـ object. في الواقع .NET بيستخدم Generational Compacting Garbage Collector: لما الـ GC يشتغل، ممكن ينقل الـ objects فعليًا في الذاكرة (عشان يقفل الفراغات اللي خلفتها الـ objects اللي اتشالت، وده اسمه compaction). العنوان اللي الـ reference بيشاور عليه بيتحدّث تلقائيًا وقت الـ GC، فالكود بتاعك مش حاسس بالحركة دي، لكن العنوان الفعلي في الميموري بيتغيّر.

في الإنتاجده بالظبط سبب وجود fixed statement وGCHandle.Alloc(obj, GCHandleType.Pinned): لو محتاج تبعت عنوان object لكود native (P/Invoke) وتسيبه شغال لفترة، لازم "تثبّت" الـ object (pin) عشان الـ GC ميحركوش وانت بتستخدم عنوانه، وإلا العنوان اللي بعته لكود C يبقى غلط بعد أول GC. ده باج نادر جدًا لكن كارثي لما يحصل (memory corruption).

public List<Student> GetTopStudents(List<Student> all)
{
    var top = all.Where(s => s.Gpa > 3.5).ToList();
    foreach (var s in top) s.Rank = "Top";   // 💥 بتعدّل نفس الـ objects اللي في all

2.3) == على الـ class: مقارنة عناوين مش محتوى

var s1 = new Student { Name = "Ali" };
var s2 = new Student { Name = "Ali" };
Console.WriteLine(s1 == s2);          // False: عنوانين مختلفين، حتى لو نفس المحتوى
Console.WriteLine(s1 == s1);          // True: نفس العنوان
Console.WriteLine(ReferenceEquals(s1, s2));  // False، نفس نتيجة ==
ملاحظة سينيور

ده هيتوسّع لما نوصل لموضوع الـ Equality (مذكور في "الخطوة الجاية"). النقطة المهمة دلوقتي: افتراضيًا، مقارنة اتنين objects بـ == أو .Equals() بتقارن العناوين مش المحتوى، إلا لو الـ class نفسه عمل override للـ Equals/== (زي ما الـ string بيعمل، وعشان كده "a" == "a" بترجع true رغم إنه reference type).

struct BankAccount { public decimal Balance; }   // ❌ فرضًا

void ApplyInterest(BankAccount acc)
{
    acc.Balance *= 1.05m;      // بيعدّل نسخة محلية بس

ملاحظة سينيور: السؤال الحقيقي مش الحجم

المبتدئ بيسأل "هو صغير؟" والسينيور بيسأل: "لو اتعمله نسخة، هل النسخة المفروض تتصرف كأصل مستقل، ولا لازم تفضل هي نفسها؟" Value (اللون، الإحداثيات، الأبعاد) → نسخة مستقلة منطقية → struct. Entity (الحساب، العربية، الطالب، العربة) → لازم تفضل نفس الكيان أينما راحت → class. الحجم شرط ثانوي (لو Entity كبير الحجم برضه، هو لسه class لأن الهوية أهم من الحجم).

شرايح 13 – 18

4) Inheritance

تشبيهعقد الإيجار العام لمبنى (الأب) بيحدد قواعد عامة (مواعيد النظافة، استخدام المصعد)، وكل شقة (الابن) ليها قواعدها الإضافية الخاصة. سكان الشقق ملتزمين بقواعد المبنى تلقائيًا، وممعندهمش خيار "ما يطبقوهاش".

4.1) ليه الـ Inheritance موجود؟ (المشكلة الحقيقية في الشريحة 16)

المشكلة

الشريحة 16 وضّحت المشكلة بشكل ممتاز: Employee وStudent بيتشاركوا Id، Name، Age، GetBirthYear(). من غير Inheritance، أي تعديل في منطق GetBirthYear() (لو مثلًا غيّرت الحساب عشان يراعي التقويم الهجري) لازم يتكرر في الكلاسين، وأي نسيان لواحد منهم = باج صامت. الـ Inheritance بينقل الملكية للمنطق المشترك لمكان واحد (Person)، فالتعديل يحصل مرة واحدة ويتطبق على الكل.

4.2) ليه C# ما بيدعمش Multiple Class Inheritance؟ (قرار تصميمي مش تعسفي)

السبب الحقيقي: Diamond Problem + الـ CLR Object Layout

لو class C : A, B واتنين الأب عندهم method بنفس الاسم Speak()، أنهي واحدة الـ C بيرثها؟ ده اسمه The Diamond Problem (لو A وB كمان بيرثوا من جد مشترك D، بيتعقد أكتر). ولغات زي C++ حلّتها بقواعد معقدة (virtual inheritance) لسه بتسبب لخبطة للمبرمجين. الـ CLR designers اختاروا يمنعوها بالكامل، ووفروا بديل أنضف: interfaces (تقدر تطبق أكتر من واحدة، لأنها عقد مش تنفيذ) وConcept الـ Composition (تحط object من نوع تاني كـ field بدل ما ترث منه).

عايز تحققهالأداة
سلوك مشترك من مصدر واحد + تخصيصSingle Inheritance (زي الشرايح)
"عقد" (توقيع methods) من أكتر من مصدرInterfaces (تقدر تطبق أكتر من واحدة)
إعادة استخدام سلوك من كلاسين مختلفين بلا علاقة IS-AComposition (الـ class يحتوي على instance من التاني كـ field)

4.3) الأنواع التلاتة (الشريحة 14): كلهم في الحقيقة نفس الآلية

الشريحة رسمت Single وMultilevel وHierarchical كأنواع منفصلة، لكن ميكانيكيًا هما نفس القاعدة: كل class ليه أب واحد بالظبط (أو object ضمنيًا لو ما كتبتش :). الفرق شكل الشجرة بس:

  • Single: B : A. أبسط حالة.
  • Multilevel: C : B : A. سلسلة، والـ C بيرث من B اللي وارث من A (يعني C بترث الاتنين).
  • Hierarchical: B : A وC : A وD : A. أكتر من ابن لنفس الأب (زي مثال Student/Employee : Person).
في الإنتاج: خطر الـ Multilevel العميقةسلسلة وراثة طويلة (E : D : C : B : A) بتخلي الكود صعب التتبع: لازم تفتح 5 ملفات عشان تفهم من فين جاية method معينة. القاعدة الشائعة: تجنب أكتر من 2-3 مستويات وراثة، وفكّر في composition بدلًا من كده لو حسيت إنك بتضيف مستوى رابع.

4.4) : base ليست وراثة "أوتوماتيك" بلا تكلفة

ملاحظة سينيور

كل member بترثه من الأب ("مجاني" ظاهريًا) بيصبح جزء من الـ عقد العام بتاع الابن. لو غيّرت حاجة في الأب، كل الأبناء بيتأثروا فورًا (كويس لو مقصود، وخطر لو مش متوقع). عشان كده مبدأ "Favor Composition Over Inheritance" شائع جدًا في التصميم الحديث: الوراثة بتخلق ارتباط قوي (tight coupling) بين الابن والأب، بينما الـ composition بتخلي العلاقة أرخى وأسهل تتغيّر لاحقًا.

شرايح 19 – 20

5) Constructors مع Inheritance

تشبيهبناء عمارة: لازم الأساس (constructor الأب) يخلص أولًا وبعدين تبني الدور اللي فوقه (constructor الابن). مستحيل تبني الدور التاني قبل ما الأساس يكون جاهز.

5.1) الشريحة 19-20: دقيقة 100%، وهنزيد عليها الآلية

الميكانيزم: ليه الأب لازم يجري الأول؟

الابن ممكن يستخدم (أو يعمل override لـ) members ورثها من الأب. لو الابن بدأ ينفذ الأول، ممكن يحاول يستخدم حاجة الأب لسه ما جهزهاش. عشان كده الـ CLR بيفرض القاعدة: constructor الأب لازم يخلص كامل قبل ما جسم constructor الابن يبدأ ينفذ. ده امتداد لقاعدة ترتيب التهيئة اللي شرحناها في سيشن 1 (قسم 3.3)، لكن هنا صريح بـ : base(name).

5.2) إيه اللي بيحصل لو ما كتبتش : base(...) أصلًا؟

class Person
{
    public Person() { Console.WriteLine("Person()"); }       // parameterless
}
class Student : Person
{
    public Student(string name) { Console.WriteLine("Student(name)"); }
    // من غير : base(...) --- المترجم بيحط : base() ضمنيًا (بينادي parameterless بتاع الأب)
}
new Student("Ali");
// Output: Person()
//         Student(name)
class Person
{
    public Person(string name) { }     // مفيش parameterless
}
class Student : Person
{
    public Student(string name) { }    // ❌ CS1729: 'Person' does not contain a constructor that takes 0 arguments
}
// لازم تكتب صراحة: public Student(string name) : base(name) { }
مفهوم غلط: "الشريحة 20 قالت لازم تستخدم base(...) لو الأب مالوش parameterless"

ده صحيح 100% وهو نفس اللي بيقوله الـ compiler error CS1729. الإضافة المهمة: القاعدة مش "لازم تكتب base(...) دايمًا"، القاعدة هي "المترجم بيحاول ينادي base() الفاضي ضمنيًا، وبيديك error بس لو مش موجود". فلو الأب عنده parameterless constructor، مش لازم تكتب base() أصلًا (زي المثال الأول فوق).

5.3) ليه الـ Constructors مش بتتورّث؟ (النقطة الأولى في "Important Notes")

السبب التصميمي

الـ constructor بيؤسس invariants خاصة بالـ class اللي هو فيه بالظبط. لو الـ constructors كانت بتتورّث زي الـ methods العادية، الابن ممكن يتعمله instance من غير ما أي كود يشتغل على الحقول اللي الابن نفسه ضافها. لازم كل class يعلن صراحةً "أنا محتاج المعلومات دي عشان أتأسس صح"، وده بالظبط عكس الفكرة اللي بعض اللغات التانية (زي Kotlin بالـ primary constructor delegation) بتحاول تبسّطها، لكن على حساب الوضوح ده.

5.4) فخ نادر لكنه موجود: virtual call من constructor الأب

ده امتداد لتحذير سيشن 1 (قسم 3.3)، لكن الآن بسيناريو Inheritance حقيقي زي الشريحة:

class Person
{
    public Person() { Describe(); }              // بينادي override بتاع الابن من جوه constructor الأب!
    protected virtual void Describe() => Console.WriteLine("Person");
}
class Student : Person
{
    private string _major = "Unknown";
    public Student(string major) { _major = major; }   // لسه ما اتنفذش وقت ما Describe اتنادت
    protected override void Describe() => Console.WriteLine($"Student majoring in {_major}");
}
new Student("CS");   // بيطبع "Student majoring in Unknown" مش "CS" ولا حتى default الحقيقي!
في الإنتاجده باج بيظهر بس في سيناريو inheritance حقيقي (زي الـ Person/Student بتاع الشريحة)، وبيبان "عشوائي" لأنه بيعتمد على ترتيب تنفيذ التهيئة. القاعدة: الأب ما ينادّيش virtual methods من الـ constructor بتاعه.
شرايح 21 – 30

6) Access Modifiers (الستة كاملين)

تشبيهشركة فيها فروع (assemblies) وموظفين وأبناء إدارات (derived classes):
  • public = لوحة إعلانات في الشارع، أي حد يشوفها.
  • internal = لوحة داخل مبنى فرع واحد، موظفين الفرع ده بس.
  • protected = معلومة بتتوّرث للأقسام الفرعية التابعة لإدارة معينة، أينما كانت (حتى لو في فرع تاني).
  • private = ورقة في دُرج مكتبك، محدش غيرك يشوفها.
  • protected internal = معلومة متاحة لكل حد في الفرع، أو لأي قسم فرعي تابع حتى لو في فرع تاني (OR).
  • private protected = معلومة للأقسام الفرعية التابعة وبس لو في نفس الفرع (AND).

6.1) جداول الشرايح 23 و27 دقيقة جدًا، هنشرح الآلية اللي وراهم

الميكانيزم: الـ CLR بيخزّن الـ modifiers دي كـ flags في الـ metadata

الـ CLR (مش C# فقط) عنده مصطلحات داخلية: Public، Private، Family (= protected)، Assembly (= internal)، FamORAssem (= protected internal، أي "family OR assembly")، وFamANDAssem (= private protected، أي "family AND assembly"). الاسمين الأخيرين بيوضحوا بالظبط ليه protected internal بيشتغل بمنطق OR (أوسع) وprivate protected بيشتغل بمنطق AND (أضيق): دول أسماء العملية المنطقية نفسها في الـ CLR. private protected اتضاف متأخر (C# 7.2) لأن دمج الـ flag ده احتاج وقت يتعرض في اللغة رغم إن الـ CLR كان يدعمه من زمان.

6.2) الفخ اللي مفيش أي شريحة ذكرته: protected عن طريق نوع الأب ممنوع

الجداول في الشرايح 23 و27 بتقول "protected: Accessible in Derived Class ✅". صحيح، لكن فيه شرط دقيق جدًا محدّش بيتوقعه، ومصدره الرسمي (Microsoft Learn) بيوضحه:

class BaseClass { protected int MyValue = 123; }

class DerivedClass : BaseClass
{
    static void Main()
    {
        var baseObject = new BaseClass();
        var derivedObject = new DerivedClass();

        // baseObject.MyValue = 10;      // ❌ CS1540: الوصول لازم يتم عن طريق نوع الابن، مش نوع الأب
        derivedObject.MyValue = 10;      // ✅ تمام: عن طريق نوع الابن
    }
}
ليه القاعدة دي موجودة؟

لو DerivedClass يقدر يوصل لـ MyValue عن طريق أي متغير من نوع BaseClass، يبقى فعليًا يقدر يعدّل حالة أي BaseClass تاني في الـ برنامج (حتى واحد مش من نوعه هو)، وده بيكسر الغرض من protected أصلًا (إنها محصورة في عيلة الوراثة بتاعتك). القاعدة بتضمن إنك بس تقدر تلمس protected members الخاصة بالـ instance بتاعك أو أبناء نوعك، مش أي instance تاني من نوع الأب أو من نوع أخ ليك (sibling class).

في الإنتاجده error بيقابل أي حد بيحاول يعمل method جوه class مشتق بتاخد parameter من نوع الأب وتحاول توصل لـ protected member منه. الحل: خلي الـ parameter من نوع الابن، أو اعمل الوصول عن طريق method عامة (public/protected) في الأب بترجع القيمة.

أسئلة مقابلات (مع الإجابات)

1) إيه الفرق بين تخزين reference type وvalue type جوه نفس الـ object؟

الـ value type field بيتخزن مباشرة جوه بايتات الـ object. الـ reference type field بيتخزن كـ عنوان (pointer) بيأشر على object منفصل على الـ heap. الاتنين ممكن يتخزنوا جوه نفس الـ object لكن بآليتين مختلفتين تمامًا.

2) هل عنوان الـ object في الميموري ثابت طول عمره؟

لأ. الـ Compacting Garbage Collector ممكن ينقل الـ object فعليًا في الميموري وقت الـ collection عشان يقفل الفراغات. الـ references بتتحدّث تلقائيًا، فكودك مش حاسس، لكن العنوان الفعلي بيتغيّر. عشان كده فيه fixed وGCHandle.Pinned لما تحتاج تبعت عنوان لكود native.

3) ليه C# مبيدعمش multiple class inheritance؟

عشان الـ Diamond Problem: لو class ورث من اتنين وكل واحد فيهم عنده method بنفس الاسم، هتبقى غامضة أنهي واحدة تتنفذ. البديل: interfaces (تقدر تطبق أكتر من واحد لأنها عقد مش تنفيذ) وcomposition.

4) لو عندي class B : A وB نفسه ماكتبش أي constructor، إيه اللي بيحصل لما أعمل new B()؟

لو A عنده parameterless constructor، الـ compiler بيولّد default constructor لـ B بيستدعي base() ضمنيًا. لو A مالوش parameterless constructor، الكود مبيتعملوش compile أصلًا (لازم B يكتب constructor صريح بـ base(...)).

5) ليه الـ constructors مش بتتورّث؟

لأن كل constructor بيؤسس invariants خاصة بالـ class بتاعه بالظبط، وبيحتاج معلومات قد تكون مختلفة عن أبوه. لو اتورّثت، الابن ممكن يتعمله instance من غير ما أي كود يهتم بالحقول اللي هو نفسه ضافها.

6) إيه الفرق بين protected internal وprivate protected؟

protected internal = (نفس الـ assembly) OR (derived class في أي assembly). private protected = (derived class) AND (نفس الـ assembly) معًا. الأول أوسع (union)، والتاني أضيق (intersection).

7) ليه الكود ده بيرمي CS1540؟ 
class B : A { void M(A a) { a.ProtectedField = 1; } }

لأن الوصول لـ protected member لازم يتم عن طريق reference من نوع الابن (B) أو نوع مشتق منه، مش عن طريق reference من نوع الأب (A). لو الـ parameter كان من نوع B، كان هيشتغل عادي.

8) ليه Bank Account لازم تكون class مش struct؟

لأنها Entity ليها هوية وحالة بتتغيّر (الرصيد) ولازم كل جزء من النظام يتعامل مع نفس الحساب فعليًا. لو كانت struct، كل تمرير أو تخزين للحساب هيعمل نسخة مستقلة، وأي تعديل على الرصيد في method أو list هيضيع بمجرد ما نطاقه ينتهي.

9) هل == بين اتنين instances من نفس الـ class بيقارن المحتوى؟

لأ افتراضيًا. == على reference type بيقارن العناوين (reference equality)، إلا لو الـ class عمل override للـ == والـ Equals (زي الـ string اللي بيعمل value equality رغم إنه reference type).

10) إيه الفرق بين Single وMultilevel وHierarchical inheritance؟

كلهم نفس الآلية (كل class ليه أب واحد). Single: B:A. Multilevel: سلسلة C:B:A. Hierarchical: أكتر من ابن لنفس الأب (B:A وC:A). الفرق شكل الشجرة بس، مش قاعدة لغوية مختلفة.

Access Modifier: اختار الأضيق اللي يفي بالغرض

  1. ابدأ بـ private افتراضيًا.
  2. لو محتاج الأبناء يوصلوا → protected.
  3. لو محتاج باقي المشروع يوصل → internal.
  4. لو محتاج الاتنين (أبناء في أي مكان + باقي المشروع) → protected internal.
  5. لو محتاج الأبناء بس وبس لو داخل نفس المشروع → private protected.
  6. لو ده API عام للمكتبة/التطبيق → public (وده الوحيد اللي بيعدّي حدود الـ assembly بحرية كاملة).

Constructor + Inheritance Checklist

  1. لو الأب مالوش parameterless constructor: هل كتبت : base(...) صراحة في كل constructor بالابن؟
  2. هل فيه virtual call جوه أي constructor؟ (لازم لأ)
  3. هل الترتيب اللي في دماغك مطابق للترتيب الفعلي (field initializers الابن → field initializers الأب → constructor الأب → constructor الابن)؟

الخطوة الجاية

  1. Polymorphism (virtual/override/sealed): الآلية الحقيقية (Method Table، vtable slots)، وليه new على method مختلف عن override، وليه sealed method أسرع أحيانًا.
